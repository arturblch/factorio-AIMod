# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

AIMod is a Factorio mod (Lua, control stage only — there is no `data.lua`) whose bot plays the game for the player: it builds small production "modules" by mining, crafting, walking and placing buildings. It targets **Factorio 2.1** (`info.json`: `factorio_version` 2.1, `base >= 2.1`); the local install is Steam Factorio 2.1.24 without Space Age.

## Running and testing

There is no build step. The mod is loaded straight from this folder through a junction `%APPDATA%\Factorio\mods\AIMod` → repo (the folder Factorio sees must be named `AIMod`, matching `info.json` and the `__AIMod__/` paths).

The Steam build refuses to start its GUI outside Steam ("Steam requires game restart"), and launching it through Steam with a custom `--config` risks Steam Cloud syncing a scratch `player-data.json` over the user's real one. So all automated runs are headless, via `tools/run-headless.ps1`. It copies the mod files of the repo to `%TEMP%\aimod-headless` (never touching `%APPDATA%\Factorio`), appends a test entry point to the copy's `control.lua`, enables only `base` and `AIMod` (any other mod in the game's `data` folder, e.g. the expansions shipped with the server build, is listed as disabled) and runs `factorio --test-scenario AIMod/AIPlay` — Factorio 2.1's headless mode **with a real player**. The script runs under Windows PowerShell 5.1 with the Steam build (default `-Factorio`) and under PowerShell 7 on Linux with the headless server build (`pwsh tools/run-headless.ps1 -Factorio <dir>/factorio/bin/x64/factorio ...`, or set `FACTORIO`); the work folder is under the system temp dir unless `-WorkDir` is given.

```bash
powershell -ExecutionPolicy Bypass -File tools\run-headless.ps1 -Unit
```
Unit tests (`tests/unit_runner.lua`): the bot is switched off and all tests run on the first tick; a few seconds. `-Brief` prints only failures and the summary. There is no per-test filter: to focus on one file, temporarily trim the `require` list in `tests/unit_runner.lua`.

```bash
powershell -ExecutionPolicy Bypass -File tools\run-headless.ps1 -Seed "1,4,42,1234567" -Brief
```
Scenario runs (`tests/scenario_test.lua`): the bot plays AIPlay on each map seed until it prints "Completed goals" or `-Ticks` (default 36000) pass; exit code 1 if any seed fails, gives up on a module, or the storage audit finds a problem. `-CursorNoise` additionally moves the player's selection onto some other nearby entity every tick before the bot runs (a mouse moving over things) and fails the seed if anything the bot didn't target gets mined; it relies on mining tasks re-selecting their target every tick. `-FullInventory` fills every empty main-inventory slot with stone bricks the first time the bot is about to mine, and fails the seed if the bot never had to make room. A seed also fails if the character dies (biters; the bot would otherwise carry on with an empty inventory). `-Goals "copper-plate:10,stone-brick:5"` replaces the bot's goal list for the run: `<item>:<n>` is a production goal (n per minute), `have:<item>:<n>` a `GatherResourceTask` (n in the inventory). `-Score` also prints the production score (`util/production_score.lua`: what the player's force made minus what it used up, at the recipe-derived prices of the game's `core/lualib/production-score.lua`) after every snapshot, per seed and in total; neither the bot nor CI uses it, and growth runs are no longer compared by it: it counts plates piling up with nothing to take them (by 30 minutes about 95 % of the iron and all the copper) as fully as plates that became buildings or research. `-Grow` lets the bot play on after its goals (`GrowthTask`, also appended to `-Goals`) until `-Ticks` and reports the modules built, their rates per minute, the electric networks (`power:` - used of capacity, consumers working or short of power, boilers and their coal, how far the research got) the supply chain (`chain:`) and the **evaluation** (`util/evaluation.lua`, plan 5.5) instead of the time: milestones (the minute the power module, a science module and each pack-researched technology on the way to `GrowthTask.RESEARCH` were reached; one not reached counts as the whole run), plates and stone used a minute (what went into buildings and research, from the production statistics; fuel doesn't count), surplus (the share of what was made that nothing used) and idle (the share of drill time the drills stood, by reason, and the bot's minutes short of something); per seed and added up at the end (milestones, their minutes and used summed, surplus and idle averaged). Runs are compared in that order (`Evaluation.better`: more milestones, sooner, more used, less surplus, less idle); `-Score` adds the old production score. A seed passes unless the character dies, mines the wrong thing or storage fails the audit. `-Modules "A,B"` makes the bot build those library modules in that order (as `/aimod-use`; `-Modules best` by score). `-Peaceful` turns on peaceful mode (biters attack only when attacked): pollution of a growing base draws attacks after ~15 minutes of game time, which would end a long `-Grow` run with the character dead (enemies are plan item 1.5). Without `-Brief` it prints goal transitions, 30 s snapshots (position, inventory, task stack, every drill/furnace with fuel/input/output) and the bot's own `output.log` summary; `-Full` prints every transition. The regression set used so far is 28 seeds: `1,2,4,6,7,8,10,12,42,1009,2018,2024,3027,4036,5045,6054,7063,8072,9081,10090,11099,12108,13117,14126,15135,31337,987654,1234567` (in test mode seeds 2k and 2k+1 give the same map). With more than one seed the run ends with "N of M seeds completed, T ticks in total" — the number `PLAN.md` compares against its baseline.

**CI.** `.github/workflows/tests.yml` runs on every push to a branch of `arturblch/factorio-AIMod` (and on pull requests from forks) on `ubuntu-latest`: it downloads the Factorio headless server for Linux from factorio.com (no account; version and SHA-256 pinned in the workflow's `env`, cached by version) and runs five parallel jobs of the same script: `-Unit`, the 28 seeds, `-CursorNoise` on seeds 1, 4, 42, 1234567, `-FullInventory` on 2, 6, 42, 1234567 and `-Goals "copper-plate:10,stone-brick:5,have:stone-brick:10"` on 1, 4, 42, 1234567. Failures show up as annotations, each job writes its result (per-seed ticks) to the run's summary page, and a failed job uploads its logs as an artifact `logs-<job>`. Results of the public repo can be read without signing in at `https://api.github.com/repos/arturblch/factorio-AIMod/actions/runs`. When the local install moves to a new Factorio version, bump `FACTORIO_VERSION` and `FACTORIO_SHA256` together (where to get them is commented in the workflow).

Logs: `%TEMP%\aimod-headless\run-<seed>.log` / `unit.log` (Factorio stdout), and the bot's log `...\data\script-output\output.log` (it holds only the last seed's run). In a normal game the bot log is `%APPDATA%\Factorio\script-output\output.log`.

A windowed run is possible only through Steam, and only after asking the user (it opens a window on their desktop and shows them as in-game): `steam.exe -applaunch 427520 --config <tmp>\config.ini --mod-directory <tmp>\mods --load-scenario AIMod/AIPlay --disable-audio`, with `<tmp>` laid out like the headless work folder (isolated `write-data`, mod copy with `require 'tests/scenario_test'` appended, so its `[test]` lines land in `<tmp>\data\factorio-current.log`). Close it with `CloseMainWindow()`.

Neither test mode nor `--benchmark` can save a game (`game.auto_save` does nothing there), so save/load is covered by the storage audit in `scenario_test.lua`, not by a real round trip.

API reference matching the installed version: `C:\Program Files (x86)\Steam\steamapps\common\Factorio\doc-html\runtime-api.json`. Check it rather than memory — 2.1 differs from 2.0 in places this code touches (e.g. `recipe.has_category()` instead of `recipe.category`, `defines.inventory.crafter_input` instead of `furnace_source`). Prototype numbers (mining speed, energy use, crafting speed, recipes, technology costs, prerequisites and research triggers) are in the game's own data: `C:\Program Files (x86)\Steam\steamapps\common\Factorio\data\base\prototypes\` (`entity\mining-drill.lua`, `entity\entities.lua`, `recipe.lua`, `technology.lua`). Guides and blueprints written for 1.x get the start of the tech tree wrong for 2.1: steam power, electronics and the red pack come from triggers, the electric mining drill costs 25 red packs (in 1.x it was there from the start), the rocket control unit is gone and several technologies were renamed (`advanced-circuit`, `processing-unit`, `research-speed-N`).

## Architecture

**Entry point and lifecycle.** `control.lua` requires every class, registers them, and exposes `AIMod.init_storage / setup_bot / tick_bot`. `on_player_created` → `setup_bot` creates a `ResourceManager` and a `GoalMachine` seeded with `AIMod.default_goals()` (production goals: 10 iron plates/min, then 20 coal/min, one module each, then `GrowthTask`, see Goals); `on_tick` → `tick_bot` for every player that has a character. The test entry points call the same `AIMod.*` functions or wrap the mod's `on_tick` (`script.get_event_handler`), so keep behaviour there rather than in the event closures.

**Classes and storage.** Classes are prototype tables (`X = Task:new()`, instances via `X:new{...}`, `self.__index = self` set lazily). All bot state lives in `storage` (`goal_machines`, `resource_managers`, `unreachable`, `path_results`, `failed_goals`, `hand_furnaces`, ...), so instances are saved with the map. **Every class whose instances can end up in `storage` must be listed in `persistent_classes` in `control.lua`** (it calls `script.register_metatable` and sets `__index` up front); otherwise after loading a save the objects have no methods and the bot crashes. No functions may be stored in `storage`. `scenario_test.lua` audits both.

**Goal machine.** `GoalMachine` is a stack (linked list) of tasks. Each tick it checks only the top task: if `achieved(args)` it is popped (nothing else runs that tick), else `tick(args)` runs. A task asks for sub-work by pushing tasks on top (`pushSingle`, `pushStart({a, b})` = a then b), and is re-ticked when they are done — so a parent's `tick` must be safe to call repeatedly and re-plan from current state. `args = {player, machine}`; tasks call `LuaControl` methods on `player` directly.

**Getting items.** `GatherResourceTask{type, qty}` means "have at least `qty` in the main inventory" (`qty` is a total, not a delta — the same convention is used by `MineResourceTask` and `CollectModuleOutputTask`). It asks `ResourceManager:best_resource_source`, which picks in order: a registered module that already has the item in its output → the nearest map entity that drops it when hand-mined (ore/tree/rock, found on demand in radii 32/100/250, derived from prototypes, skipping ore under our buildings and anything in `Unreachable`) → hand-crafting → a module that must first be fueled and waited on → researching the technology that unlocks its recipe, when research triggers alone do it (`ResearchResourceSource` pushes `ResearchTriggerTask`, which makes the trigger item until the game marks the technology researched, trigger prerequisites first; in 2.1: 50 iron plates → `steam-power` (pipes, boiler), 10 copper plates → `electronics` (cable, circuits, lab, inserter, small pole), a lab → `automation-science-pack`) → building a module from `ModuleLibrary` that makes it (`BuildModuleResourceSource`, the cheapest module that makes it; not a module a `BuildModuleTask` on the stack is already building, nor one making the same product). The last two are not for `optional` gathers. When no module can be built for it either (the one that would make it is being built and lacks this very item, or all were given up on), a smelting product comes from hand smelting (`HandSmeltResourceSource` → `HandSmeltTask`): otherwise a growth column of iron waited forever for plates once the only iron pair ran out of ore. Each source's `gather` pushes the concrete tasks. `CraftRecipeTask` uses `util/recipes.lua` to expand intermediates recursively and only gathers raw items; the game's hand-craft queue makes the intermediates. With `background = true` (used for module buildings) it is done once the crafts are queued; `Inventories.count_with_queue` counts queued items and `PlaceBuildingTask` waits for them. Without it the task is done only when the whole hand-craft queue is empty, background crafts queued before it included, and the bot does nothing meanwhile: 10 red packs (`ResearchTask`'s batch) are 50 s of standing (plan 4.9).

**What tasks need.** Tasks report what they still want in the inventory via `needs(args)` (`{name = total}`; `GoalMachine:needs` takes the largest total per item over the stack). This decides what `MakeRoomTask` keeps when the inventory is full (the rest goes into a stash chest, registered as a `ChestResourceSource`) and what `WaitForOutputTask` fetches from the map while a module works. A new task that will consume items should implement `needs`.

**Waiting for a module.** `ModuleResourceSource:gather` pushes `WaitForOutputTask{qty, total}`: done when the module's outputs hold `qty`, or hold together with the inventory the caller's `total`. `qty` is at most what the outputs can hold (`BaseModule:outputCapacity`: a coal pair holds 2 × 45, and a wait for 94 never ended); the gather comes back for the rest. Meanwhile it first fetches the needs of the tasks below it from the map, then mines its own item by hand where the map has it, 10 at a time (`GatherResourceTask{from_map = true}`, which only takes the map: a module source would send it back to the wait; before, the bot stood by a stone chest making 15 a minute for its 40 stone), then (once per wait, if the module needs ≥ 10 s more) pushes a `HandSmeltTask`: the bot crafts a stone furnace, places it by the ore (kept in `storage.hand_furnaces[player][ingredient]` and reused; one still being built is in `storage.hand_furnace_builds`, so the next task finds it even when the one that placed it was done first), mines one ore at a time and feeds it, so plates come from hand mining as well as from the drill (a burner drill mines 0.25 ore/s, a stone furnace smelts 0.3125 plates/s). `HandSmeltTask{keep}` leaves in the inventory what the tasks below need (stone for drills, their fuel), or it would cost a second trip later.

**Goals.** A goal is a product: `ProductionGoalTask{item, per_minute}` is achieved once the working registered modules make that much (`BaseModule:productionRate`, items/s derived from prototypes: drill mining speed, recipe time and ingredient count, minus what the module's own burners take of a fuel product); until then it pushes a `BuildModuleTask` for the first `ModuleLibrary.producer` of the item, so a larger goal builds several modules. Its `needs` are those of the module it would build next. A goal that can't be met (no producer left, or a new module added nothing) is recorded in `storage.failed_goals` like a module. `GatherResourceTask` works as a "have N" goal: it reaches modules through `BuildModuleResourceSource`. The default list ends with `GrowthTask`, which never stops: each tick it first looks after the modules: once a burner the bot fuels has < 5 coal, a refuel round (`GrowthTask.fuel_round`, plan 4.7) tops up every burner below 10 to 20 - unless the inventory holds that much, the bot first takes all the coal waiting in the coal modules (`CollectModuleOutputTask{all = true}`), gathers the rest, then visits the burners nearest first, and keeps what is left for the next round; else it empties the nearest half full output. Then it pushes a `ProductionGoalTask` just above the current rate of the next product, i.e. one more module (`GrowthTask.plan`), chosen by the planner, model predictive control in three levels (plans 2.7-2.12) with no tuned pace or timer. **Strategy** (`util/strategy.lua`): `Strategy.targets` - each final product's `GrowthTask.MIX` share scaled up to the product furthest ahead of its share, plus what the labs take of it for the research under way (the supply chain's research demand) -, and `Strategy.roadmap` - the pack-researched technologies for `GrowthTask.RESEARCH` in order, prerequisites first through the game's tree (it drives `GrowthTask.electricity` and `next_research`). **Tactics**: `GrowthTask.candidates` are one module per item - the `ModuleLibrary.producer` of each MIX product (the shares only pick the very first module, when nothing runs yet), of the fuel, and of each raw item their buildings take that a module makes (stone) -, cut by `GrowthTask.shortlist` to `MAX_CANDIDATES` (5: the fuel and building materials, then the final products furthest behind their targets); `GrowthTask.prepare` sets up an `Economy.search` from `Economy.state` (the working modules, the inventory with candidate buildings counted as their raw cost, module outputs and the coal in burners less 20 a fuelled burner - spoken for by refuel rounds - and the calibration), and **`PlanTask`** (`controllers/tasks/plan_task.lua`) runs it `RUNS_PER_TICK` (16) model runs a tick, the search being plain data in storage (no coroutines in Factorio; a joining multiplayer client gets it); then `GrowthTask.decide` builds the first module of the best plan. The search (`Economy.search_step`) is a beam: every candidate first, then for the `BEAM` (4) best plans one more candidate each, `DEPTH` (4) deep, each plan run to `Economy.HORIZON` (25 min) and on with `Economy.carry_on` (the coal module while the coal modules make less than the burners burn with one more plate column or the stock lacks the coal to stock it, else the column of the final product furthest behind its target) - 52 runs where trying every order took 256, and the same choice on the tested states. The goal (`Economy.better`) is not points: first **development** (the plates a minute of the final products, every plate the same, the modules make at the end of the horizon, as far as the coal modules keep the burners going), within `DEVELOPMENT_TIE` (1/min) less **shortage** (the minutes the bot spent waiting for or getting by hand what it lacked, by item), within `SHORTAGE_TIE` the product furthest behind its target; with points (copper plates 6.32, iron 5.63) it built copper column after copper column. The model (`Economy.start/advance/finish/clone`, plan 2.10) goes from event to event (a module built, a lacking item there, the coal gone, the horizon) with constant flows in between, about 0.1 ms a 25-minute run (`Economy.run_stepped`, the old 6-second steps, is kept for the tests): modules make `ModuleLibrary.report` rates times their **calibration** (`util/calibration.lua`, plan 2.12: every 5 s the share of each item's drills at work, weighted by rate, as a running average; used after a minute of samples, else `COAL_DELIVERY` 0.75 for coal) into one stock and burn `fuelUse` from its coal (with the coal gone they work as far as the coal coming in keeps them); the bot builds from raw cost plus 20 coal per burner, mines by hand what it lacks (stone, coal 30/min, wood 60/min), else smelts lacking plates by hand (15/min), else waits; building takes 30 s + 5 s per building; every module it fuels or empties takes 2 s of its time a minute. Measured burning (coal burnt over the paper rate) made it build too many coal rings and is out. `sim.score` still holds the production score. `util/bottleneck.lua` still counts what the bot spends time on (waiting for a module, smelting or mining by hand) in `storage.time_spent`, but only for the log now. The supply chain (`util/supply_chain.lua`, plan 2.6: per item the working modules' rate against `burn`, `build` - the planned module over `SupplyChain.BUILD_MINUTES` - and `research` demand, with the stock on hand and the production statistics of the last 10 minutes) explains the state: `/aimod-chain` prints the planner's ranking and the links, scenario `-Grow` runs log a `chain:` line. Its first tick calls `AIMod.goals_done` ("Completed goals"), which is where scenario runs without `-Grow` stop, as before. It is achieved only when every producer was given up on. Between upkeep and the next module it takes the electricity step (`GrowthTask.electricity`): once `ELECTRICITY_AFTER` (4) modules run, the power module `SteamPower`; then `GrowthTask.RESEARCH` in order (automation, then the electric mining drill), each once the one before is researched: first a module of `GrowthTask.SCIENCE_MODULES` making its packs (`RedScience`) if we have none and the force can craft all its buildings (the assembling machine waits for automation), then a `ResearchTask` while the labs lack packs for it.

**Modules.** A module (`BaseModule`) is data: `geometry` (tiles relative to tile 0,0 with required ore), `buildings` (type, center relative to the *corner* of tile 0,0 — a 2×2 at `{1,1}` covers tiles 0..1 — and direction), `inputs` (fuel slots; `ongoing = false` only to start it) and `outputs` (`slot = "output"` result inventory or a chest's inventory, or `"fuel"` surplus above `keep`). Modules come from **blueprints**: `blueprints/library.lua` lists them in order of preference (name, blueprint string or a key of its `BLUEPRINTS`, `resource`, optional `product`, `off`), and `util/blueprint.lua` turns a blueprint string (`helpers.decode_string` + `helpers.json_to_table`, both usable while `control.lua` loads) into module data from prototypes by following the items: ore tiles = the drills' mining areas; a drill drops at `vector_to_place_result` onto a building, a belt or the ground; a belt carries to the belt in front (straight or side-loading), an underground belt to its exit (blueprint `type` input/output, kept as `building.belt_end`), a splitter to both belts ahead, never into a building; an inserter moves from `inserter_pickup_position` to `inserter_drop_position` (a burner inserter carrying coal fuels itself); an assembling machine makes the blueprint entity's `recipe` (kept as `building.recipe`, `PlaceBuildingTask` passes it to `create_entity`) and an inserter can take its products; a lab takes the science packs it gets (the module's `packs`); outputs are furnace results or assembling machine products no inserter takes away, chests that receive something, or coal in drills fed by the module; inputs are every burner that gets no coal from the module (of those that do, only the first, to start) and the ingredients of assembling machines no inserter brings (`slot = "input"`). A module without drills needs no `resource`; one with buildings on electricity and no generator is `powered` (it must have a pole). Its third result are **checks**: errors (a drill dropping on the ground, an inserter with nothing to take from or nowhere to put, nothing the bot can collect) leave the module out of the library; warnings (a belt carrying nothing, a belt ending with items no inserter takes, a furnace with nothing to smelt) are shown. `ModuleLibrary.report(module)` adds the numbers to compare variants: rates, raw build cost (recipes down to plates, stone, wood), coal a minute the bot brings and buildings it fuels, minutes until an output is full, furnace load (drills' feed over furnace capacity, warned below 0.75 or above 1.25) and score = (value made − coal burnt) a minute / build cost, at the production score's prices. `ModuleLibrary.producer` keeps the list order, except that while no working module makes the item it skips modules whose build lacks some of that very item beyond what the player carries (`missingOwn`: the belt line needs 64 more iron plates than the starting kit), and that a goal of N a minute (`ProductionGoalTask:shortfall`, not set for `growth` goals) first takes the cheapest module that alone makes what the goal lacks, unless the modules were chosen by name. The library lists several pairs in one place first (`IronColumn4`, `CopperColumn4`: four drill → furnace pairs back to back; `CoalRing4`: four coal drills feeding each other), so growth builds those (fewer stops to fuel and empty) while the goals and the start take the single pairs. `controllers/modules/library.lua` builds them while loading (`ModuleLibrary.listed/all/get/producers/producer/choose`; a broken entry is logged and left out) and keeps the old global names (`BurnerToFurnaceModule`, `BurnerToBurnerModule`, ...). `ModuleLibrary.choose(names)` / `/aimod-use` override which modules are built and in what order (`storage.module_choice`; `best` ranks every listed module by score, and takes the cheapest covering module for a goal as the library's order does). `blueprints/found/catalog.lua` (with a `README.md`) keeps 127 community blueprints from Factorio Prints for later, not built by the bot: burner-era layouts and small steam plants, each with its source, a 2.x string and `fits` (resource → score where `Blueprint.module` takes it with no errors); `node tools/found-blueprints.js fetch|build|checks` downloads entries, rewrites the catalog and fills in `fits` from the file `tests/unit/found_blueprints_test.lua` writes (that test also fails when a fitting entry stops fitting). `blueprints/src/*.json` are the sources of the bundled strings; `node tools/blueprint.js show|decode|encode|viewer` draws, decodes and makes strings and refreshes `tools/blueprint-viewer.html` (published as the claude.ai page "Чертежи бота AIMod", https://claude.ai/artifact/KigbcDdzwN4NGhYHhQ74t8: the library, the found catalog and `blueprints/trials.json`, the growth runs' results, kept by hand). While a module is being built, `ModulePlan` (`controllers/modules/plan.lua`) draws it on the ground with `rendering`; `/aimod-modules` lists the library with each report and its warnings, `/aimod-plan <name>` shows for a minute where the bot would build one. `BuildModuleTask` first builds its *foundation*: a module making a raw material of its buildings that only a module can make (iron plates for drills) when no working module makes it yet — so the start's single drill and furnace always go to iron. A building whose recipe is still locked is researched first when triggers unlock it (`ResearchTriggerTask`: the power module's lab and pole wait for electronics, 10 copper plates), else the module is given up on (a `CraftRecipeTask` of a locked recipe waits for ever). Then it finds a spot (`findLocation`: the nearest ore tile of the module's resource that can stand for the module's first ore tile, `BuildModuleTask.anchor`, so only the drills need ore and only of their own kind; searched from the nearest module of ours on the same resource, so modules go in rows along the patch, else from the player), crafts missing buildings, then builds a private `instantiate()`d copy, queues fuel for it and registers it as a `ModuleResourceSource`. It is achieved only when every building stands; otherwise it picks the placed ones back up (`mine_entity`), avoids that spot and retries (3 attempts), then records the module in `storage.failed_goals`.

**Electricity.** A power module is a blueprint with `resource = "water"` (`blueprints/library.lua`: `SteamPower` - an offshore pump facing the water, a boiler, a steam engine, a small pole and a lab). `util/blueprint.lua` reads it as `power = true` with no outputs: the tiles the pump needs water on (its prototype's `tile_buildability_rules`) are geometry tiles with `tile = "water"`, the pump's own `shore = true`; the boiler is an input (coal); it warns when a pole doesn't reach a generator or consumer. `BuildModuleTask:findLocation` searches the shore (water tiles next to land) from the nearest module of ours, and `canBuildAtPosition` asks the game whether a pump may stand there (`can_place_entity` with `build_check_type.manual`). Its coal (`BaseModule:fuelUse`) is what the engines deliver now, not the boiler's 1.8 MW. `util/power.lua` reads the force's electric networks: production and capacity of the generators, consumers per name with how many work or are short of power, boilers and their fuel (`Power.lines` for `/aimod-power`, `Power.summary` for the scenario runs' `power:` line). `ResearchTask` researches a technology that costs packs: queues it, hand-crafts packs in batches of 10 and carries them into a lab with power; it is done once the labs hold the rest of what it takes, so growth goes on while the lab works. Where an assembling machine of ours on a network makes the pack (`ResearchTask.assemblers`), it carries the machine the ingredients for up to 50 packs instead (copper plates and gears for red ones), and what the machine will make of them counts as in the labs. That machine is a science module: `RedScience` (an assembling machine making red packs, an inserter into a lab, a small pole) has no resource and is `powered`, so `BuildModuleTask:findPoweredLocation` first tries to put it with its own lab on a lab of ours (`findAtOurLab`: the power module's, west of it in the bundled layouts) - the inserter then feeds that lab, and the module's lab is neither built nor picked up again (`BuildModuleTask.reuse`, building index -> entity) - else puts its pole as close as it can to a pole of ours on a network within both poles' wire reach (the game wires them); either way off ore. In 2.1 the steam power and electronics technologies come from triggers (50 iron plates, 10 copper plates; `ResearchTriggerTask`), the electric mining drill and the assembling machine (automation) only from packs (25 and 10). Throughput: an assembling machine 1 (speed 0.5) makes a red pack in 10 s, 6 a minute - what one lab (speed 1) uses on a technology of 10 s a unit (automation, the electric mining drill); one of 5 s a unit (`logistic-science-pack`, `steel-processing`) takes 12 a minute, so two machines a lab (plan 3.14).

**Evaluation.** `util/evaluation.lua` (plan 5.5) watches the base in every game, not only in tests: `Evaluation.tick` notes each milestone's tick (every 60 ticks) and samples the drills' statuses (every 300) in `storage.evaluation`; `Evaluation.report` adds the production statistics and `util/bottleneck.lua`'s time; `/aimod-evaluation` prints it, scenario `-Grow` runs log it (`evaluation:` and the `evaluation-key` line `run-headless.ps1` adds up). The planner's own goal (development: plates a minute) is not this yet - it still builds plate columns that end up as surplus.

**Walking.** `MoveToPointTask` steers with "feelers" that dodge trees and rocks (the original author's approach). If the character makes no progress for `STUCK_TICKS` it asks the game's pathfinder (`surface.request_path`; the answer arrives via `on_script_path_request_finished` into `storage.path_results`) and follows the waypoints; if that also fails the target entity goes into `Unreachable` and callers pick something else. `reach = true` ends the walk as soon as `can_reach_entity` holds (needed for big rocks). Ore must be walked onto — hand-mining reach is short.

**Scripted control state sticks.** A `walking_state` or `mining_state` set by script persists until changed (a real player's input does not reset it in headless runs). Tasks therefore reset it when they finish (`MoveToPointTask`, `MineResourceTask`, `MineEntityTask` do this in `achieved`). An earlier test harness that reset walking itself hid exactly this bug — prefer testing with the real player.

**Unused code.** `controllers/tasks/pathfindToPointTask.lua` and `util/pathfinding_fringe.lua` are an unfinished A* from the original author; nothing calls them (the game pathfinder is used instead).

## Factorio Lua specifics

- `require` resolves relative to the requiring file first, then the mod root, then `core/lualib`; `..` is not allowed. `require 'util'` therefore loads the core `util` library (this repo's `util/` is a folder), while `require 'util/logger'` loads the repo file.
- Use `storage`, `helpers.write_file`, `prototypes.entity[...]`, `defines.inventory.character_main` (2.x names).
- With a full main inventory the character can't mine: the mining bar keeps filling and nothing is mined or dropped. An entity with several products (a huge rock: stone and coal) is only mined when all of them fit at once. A hand-craft takes its ingredients when queued, and a finished craft waits until its product has a slot, stalling the whole queue. Mining, collecting and crafting tasks check room first (`Inventories.has_room_for` / `has_room_for_all`) and push `MakeRoomTask`.
- The character mines whatever is selected (`mining_state` only says *that* it mines). Selecting by position (`update_selected_entity`) is ambiguous: tree selection boxes are tall (tree-02-red: 1.8 × 2.8 tiles) and overlap, and the game picks the tree in front, so a point on the target can select its neighbour. `MineEntityTask` therefore assigns `player.selected = entity`, which selects exactly that entity if it is selectable, and checks it took before mining.
- Logging goes through `Logger.makeLogger("Name")` → `log(msg, level)`; `Logger.LEVEL` in `util/logger.lua` filters (DEBUG logs every steering step).

## Tests

- `tests/lib/testing.lua` — minimal `describe`/`it`/`before_each` with `T.eq/same/near/truthy/falsy`. `describe` bodies run when the file is loaded, before `game` exists: create anything that touches the game inside `it`/`before_each`.
- `tests/lib/fakes.lua` — a fake player/inventory that records what the bot did (`printed`, `crafted`, `mined`, `walking_state`...) and a fake pathfinding surface; recipes, prototypes and surfaces are real.
- `tests/lib/lab.lua` — a separate surface generated with no ore, trees, cliffs or enemies; `Lab.reset()` flattens the area to grass and tests place exactly what they need (`Lab.ore`, `Lab.patch`, `Lab.water`, `Lab.entity`).
- `tests/unit/planner_test.lua` — the planner's goal, why iron or copper, the event model against the stepped one, the beam against trying every order, the search a few runs at a time and as plain data, calibration in the model; `tests/unit/strategy_test.lua` — roadmap, targets, shortlist, calibration.
- `tests/unit/chain_sequence_test.lua` — from the start of growth with a given stock, the planner picks four modules one at a time (the base and stock put on the lab each time) and the economy model runs 25 minutes with them, then `Economy.carry_on`; it must reach at least 90 % of the development of the best of all 256 orders at 30 minutes. `tests/unit/planner_test.lua` pins down the goal and why iron or copper comes first. Each case logs both orders as `[unit] NOTE` lines (shown by `-Unit` without `-Brief`).
- A new test file must be added to the `require` list in `tests/unit_runner.lua` (Factorio cannot list directories). Shared storage keys are reset in `T.global_before` there.
